# Windows 파일·사진 전송 후속 QA

최신 판정(2026-10-27): **이미 열린 자기방에 TXT70B·PNG사진5,931B를 각1회 보내고, 새 수신 행과 원본·다운로드·회수본 SHA-256 일치를 확인했다.** 전송부터 해시 확인까지 새로 표시된 카카오톡 최상위 창0개·전면 전환0회였다. 아래에는 각 실험의 조건과 차단 기록을 날짜별로 구분한다. 배포 스킬은 여전히 읽기 전용이다.

## 확인창을 허용한 2026-10-19~20 실험

검증일: 2026-10-19~20. Windows KakaoTalk 26.8.2.5324 x64, Python 3.14의 본인 로그인 계정에서 무해한 TXT 1개와 PNG 1개를 자기방에 보냈다. 두 건 모두 실제 메시지와 서버 파일을 다시 읽어 원본과 비교했다.

PNG 전송 확인창에는 ‘파일 전송’이라는 제목이 표시됐다. 이 제목만으로 일반 파일 첨부라고 판정하지 않았다. 전송 후 실제 저장된 메시지 종류가 type 2였고, 그 메시지의 원본 이미지를 서버에서 내려받아 해시까지 일치했다.

## 검증한 흐름

1. 실행 파일 해시·새 PID·본인 계정과 자기방을 확인한다. 기존 창·작성 중인 글·다른 확인창을 검사한다.
2. 파일명·크기·SHA-256을 고정하고 자기방 HWND에 `WM_DROPFILES`를 한 번 전달한다. 이는 전송 완료 증거가 아니다.
3. 해당 자기방이 소유한 확인창만 `PrintWindow`로 캡처한다. 실제 파일명·크기·버튼을 확인한 뒤, 같은 픽셀 해시와 창 소유자를 재검증하고 해당 창에만 버튼 메시지를 보낸다.
4. 같은 자기방을 별도 읽기 경로로 다시 조회한다. 사전 조회보다 새 메시지인지, 본인 발신인지, TXT는 type 18·PNG는 type 2인지 확인한다.
5. 해당 QA 메시지의 서버 파일만 제한된 크기로 내려받아 원본과 해시를 비교한다. 첨부 URL·키·토큰·원문 JSON은 기록하거나 공유하지 않는다.

## 실행 세션과 RAM

WSL의 기존 실행 통로가 사용자 세션 1에서 세션 0으로 바뀌는 현상을 재현했다. 다른 세션의 창을 찾지 못한 것을 ‘채팅창이 닫힘’으로 판정하면 안 된다. 세션·station·desktop이 맞지 않으면 입력 전에 차단해야 한다.

이후 기존 탐색기의 Shell 자동화로 창 없는 임시 도우미를 실행해 **Session 1 / WinSta0 / Default**를 실측했다. 서비스·예약 작업을 설치하지 않았고, 각 작업은 실행 전에 같은 조건을 다시 검사했다. Shell 자동화는 Microsoft가 설명하는 [탐색기에서 실행하는 방식](https://learn.microsoft.com/en-us/windows/win32/shell/samples-execinexplorer)과 [ShellExecute 인터페이스](https://learn.microsoft.com/en-us/windows/win32/shell/ishelldispatch2-shellexecute)를 사용한다. 이 환경의 성공이 모든 Windows 세션에서의 연결 보장은 아니다.

| 자원 | 실제 측정과 제한 |
|---|---|
| 발신·읽기 도우미 | Job 전체 256MiB. 실제 발신 검사 최고 106,344,448바이트 |
| Shell 도우미 | Job 전체 256MiB, 25초. 이번 PNG 전송 확인 최고 34,152,448바이트 |
| 카카오톡 감시 | private 2GiB 및 기존 기준 +128MiB 전에 작업 차단. 앱 자체에 OS 메모리 할당 제한을 새로 적용한 것은 아님 |
| Windows 카카오톡 마지막 private | 320,032,768바이트, 약 305MiB |
| Mac 카카오톡 마지막 RSS | 38,813,696바이트, 약 37MiB. Windows private와 다른 측정 지표 |
| 남은 분석·QA 프로세스 | 이번 작업의 Windows 도우미와 Mac Java/Node/Claude 분석 프로세스 0개 |

정적 분석은 단일 JVM, heap 1GiB·프로세스 그룹 RSS 1.5GiB·시간 상한을 유지했다. 분석과 발신이 끝난 뒤 프로세스가 종료된 것을 별도로 확인했다. 불확실한 발신은 같은 영수증부터 읽고 자동 재전송하지 않는다.

## 팀에서 사용할 범위

현재 배포 스킬은 계속 **읽기 전용**이다. 방 찾기·닫힌 방 읽기·과거 검색은 [기존 QA](QA.md)의 범위를 따른다. 이번 결과는 소유자가 허용한 자기방 TXT·PNG 두 건의 별도 실험이며, 임의 방·다른 계정·다른 빌드·DPI·확인창 구성을 검증한 공용 발신 기능은 아니다.

확인창 없는 Windows 발신은 아래 v4 조건에서 실물 검증했다. 닫힌 방으로의 발신, Mac 첨부, 임의 파일·다른 방을 지원하는 공용 발신 CLI는 남은 항목이다. 내부 함수 주소를 찾았다는 사실을 외부 CLI 호출 성공이나 실제 수신 성공으로 계산하지 않는다.

## 확인창 켜짐 상태의 후속 조사: v3 과거 기록

2026-10-20 v3 조사 시점에는 **확인창 없는 실제 발신이 미검증**이었다. 이 구간에서는 새 파일·사진을 보내거나 확인창을 띄우지 않았고, 화면 입력·클립보드·설정·기기 로그인 전환도 사용하지 않았다. 이후 v4 성공과 구별해 당시 결과를 보존한다.

Windows의 내부 파일 처리에는 확인창 설정에 따라 바로 처리하는 분기가 있다. v3 당시 설치본의 실제 설정은 확인창 켜짐이었으며, 그 설정을 적용하는 앱 상태도 읽기 전용으로 대조했다. 다른 직접 호출자는 기존 첨부 객체와 확인 결과를 받는 내부 callback이었다. 당시 비교한 외부 파일 드롭 구현 역시 확인창을 자동 확정하는 방식이었다. 내부 함수 주소를 외부 발신 API로 취급하지 않는다.

Mac에는 확인 강제 플래그가 0인 호출자가 있지만, 별도의 일반 파일 확인 설정을 다시 검사한다. 앱 URL 처리에는 창을 표시하는 경로도 있다. 조사한 외부 진입점에서 방·파일·화면 비표시를 함께 지정하는 규격은 확보하지 못했다. 현재 상태에서 로그인만 Mac으로 전환해도 실제 발신 QA를 시작할 준비가 된 것은 아니다.

|---|---|
| Windows 확인 설정과 앱 상태 실측 | PASS: v3 당시 확인창 켜짐 |
| Windows 무화면 TXT·사진 송수신 | v3에서는 NOT RUN; 이후 v4 결과는 아래 |

이 후속 조사도 배포 스킬에 발신 기능을 추가한 결과가 아니다. 확인 설정을 임시 변경하거나 창을 띄운 뒤 숨기는 동작을 팀용 무화면 기능으로 제공하지 않는다.

## 확인창 없는 Windows 발신: v4 실물 결과

2026-10-20 사용자가 일반 파일 확인 옵션을 끄고 알림 팝업도 임시로 끈 뒤, 기존 로그인 세션의 이미 열린 자기방에서 TXT1건·PNG사진1건을 보냈다. AI의 설정·클립보드·포커스·커서 조작은0회다. 2026-10-23에는 저장된 실제 영수증2개를 현재 완료 판정 함수로 다시 평가하고, 받은 파일2개와 실행 소스8개의 해시가 당시 기록과 같은지 대조했다. 모두 일치했으며 새 발신·앱 재조회는 수행하지 않았다.

고정 QA용 실험기의 검증 결과이며 배포 스킬에 발신 기능을 추가한 것은 아니다. 임의 파일·다른 수신자·닫힌 방·화면 잠금·로그아웃·다른 앱 버전과 미래의 화면 불변은 미검증이다. 앱이나 로그인된 데스크톱 없이 발신할 수 있다는 증거도 아니다. Mac 첨부는 외부 진입 계약 미확보와 실제 송수신 미검증 상태를 유지한다.

## 2026-10-23 사전검사 차단 기록

사용자가 새 자기방 TXT70B·PNG5,931B 각1회 이하 시험을 승인했다. 앱26.8.2.5324·Windows 사용자 Session1·기존 소스 해시는 일치했고 앱 RAM도 기존 상한 아래였다. 그러나 당시 확인 옵션 키 미관측·기본값yes·preview_enabled=true가 반환돼, 앱의 확인창 OFF 적용을 검증하지 못했다. 확인창 OFF를 요구하는 실행기가 발신 전에 차단했으며, 실제 확인창을 띄워 시험한 결과는 아니다.

이 단계의 새 발신 TXT0·PNG0, 새 수신·다운로드 NOT_RUN이다. 자기방·입력칸 검사는 이보다 뒤 단계라 실행하지 않았다. 두 요청의 발신 ledger·내용별 claim 없음과 당시 도우미 잔존0을 확인했다. 카카오톡 로그인 여부를 확정하거나 설정·보안·화면을 변경하지 않았다. 과거 v4 성공을 당시 환경의 발신 성공으로 승격하지 않았다. 이 결과는 발신 실험에 관한 것이며 읽기 스킬의 변경·재배포가 아니다.
